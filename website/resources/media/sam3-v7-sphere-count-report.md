# V7 碰撞球数量对完整规划耗时的影响

2026年11月27日。

碰撞球数量会影响耗时，但减少球数不能把当前完整规划直接压到几十毫秒。本轮871、512、256球的完整请求平均分别为5.669、4.355、4.381秒，512球继续减到256球没有进一步收益。主要秒级开销仍集中在反复绑定机器人与场景、处理完整配置和更新接触几何。执行配置继续保留871球。

## 怎么比较

采用苹果、甜甜圈、香蕉、芒果、剪刀五份已冻结观测。三档模型各重复两遍，共30次普通完整规划；871球另做两次全请求剖析，用于定位CPU与GPU调用。候选、排序、实际夹爪宽度、初态、32个IK初值、规划精度、TCP43和指尖桌面余量均沿用原设置。

512和256球由同一连杆上的原球保守合并得到：大球完整包住原小球，每个原球的覆盖关系都独立核验。三档只在各自子进程加载，不改默认配置。

完整规划按512→256→871三组执行；固定工作量测试让三档在同一张卡上交替运行。完整请求表反映本轮观察到的总差异，固定工作量表用于看球数对GPU计算本身的影响。

## 完整规划

| 碰撞球数量 | 规划通过 | 平均耗时 | 中位数 | P90 | 候选检查总数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 871 | 10/10 | 5.669秒 | 5.267秒 | 8.864秒 | 70 |
| 512 | 10/10 | 4.355秒 | 4.079秒 | 6.449秒 | 70 |
| 256 | 10/10 | 4.381秒 | 4.090秒 | 6.195秒 | 70 |

512球相对871球的本轮平均耗时减少23.2%，256球减少22.7%。三档都检查70个候选，同场景选中的抓法、左右臂、开度和候选拒绝原因均相同。

规划数值轨迹存在变化：512球相对871球的最大关节终点差为0.0006130弧度；256球的关节终点相同，但完整路径也有变化。三档都通过原独立末端FK和关节限位复核。

## 秒级时间花在哪里

下表为一次完整请求的平均值，使用扣除子调用后的耗时，各行可以相加。

| 完整请求中的环节 | 871球 | 512球 | 256球 |
| --- | ---: | ---: | ---: |
| 机器人与场景绑定 | 2.745秒 | 1.960秒 | 1.933秒 |
| 开合爪模型读取、FK与碰撞检查 | 0.311秒 | 0.218秒 | 0.177秒 |
| 抓取IK与终点核验 | 0.846秒 | 0.694秒 | 0.707秒 |
| 接触几何更新 | 0.691秒 | 0.557秒 | 0.619秒 |
| 预抓取与抬升IK | 0.031秒 | 0.026秒 | 0.029秒 |
| 路径搜索与轨迹优化 | 0.396秒 | 0.292秒 | 0.284秒 |
| 其余交接、调度与记录 | 0.649秒 | 0.608秒 | 0.632秒 |
| 合计 | 5.669秒 | 4.355秒 | 4.381秒 |

每次请求平均仍绑定13次机器人与场景。871→512球时，绑定一项就从2.745秒降到1.960秒，贡献了约0.785秒的总差异。球越多，完整配置的解析、写出、复制和校验也越重。

## 同一工作量的GPU计算

每个场景固定256个关节状态：96个来自同一条已通过的871球轨迹，160个为同一种子生成的限位内状态。三档始终使用相同关节数组、实际开度和场景；没有IK、候选搜索或路径规划。共检查每档1280个状态。以下为五个场景各自测量中位数的中位数，计时范围为CUDA Graph重放。

| 同一批关节状态数量 | 871球 | 512球 | 256球 |
| ---: | ---: | ---: | ---: |

| 32 | 0.0434毫秒 | 0.0373毫秒 | 0.0333毫秒 |

| 同一批关节状态数量 | 871球 | 512球 | 256球 |
| ---: | ---: | ---: | ---: |
| 1 | 0.0111毫秒 | 0.0115毫秒 | 0.0112毫秒 |

少量状态的碰撞检查已经只有约0.01毫秒，继续减少球数的绝对收益很小。一次检查256个状态时，世界碰撞从约0.566毫秒降到0.349毫秒，减少约38%；完整状态验证从约0.607毫秒降到0.386毫秒，减少约36%。这部分有收益，但量级仍是毫秒以内。

当前设置的原生自碰撞检查为关闭，停放臂作为世界障碍物检查；本轮保持原设置。

## 模型数量带来的CPU处理成本

取三档实际参考配置，对读取、写出、深复制和球参数散列在CPU上交替各测15次。下表为单次操作中位数。

| 配置操作 | 871球 | 512球 | 256球 |
| --- | ---: | ---: | ---: |
| C版YAML解析 | 31.02毫秒 | 17.13毫秒 | 8.61毫秒 |
| C版YAML写出 | 25.23毫秒 | 15.47毫秒 | 7.75毫秒 |
| 深复制 | 3.22毫秒 | 1.75毫秒 | 0.90毫秒 |
| 球参数散列校验 | 2.05毫秒 | 1.56毫秒 | 0.79毫秒 |

球数会同时增加GPU几何计算和CPU配置处理。完整请求中重复做这些配置操作，更容易积成几百毫秒到数秒。

## 全请求剖析发现

苹果与香蕉各做一次CPU/CUDA剖析。剖析会增加耗时，未纳入上面的30次普通规划。

| 检查项 | 苹果 | 香蕉 |
| --- | ---: | ---: |
| 写出YAML次数 | 6 | 25 |
| 加载碰撞场景次数 | 14 | 69 |
| 记录到的GPU内核累计 | 0.166秒 | 1.313秒 |

GPU已记录内核中，碰撞相关内核占约73%和78%。这表示GPU内部主要在做碰撞计算，不能把这个比例直接当作整次规划的碰撞占比。CPU还在重复写配置、装载场景、转换历史路径、计算散列和排序网格。

## 少球模型改变了什么

| 模型 | 原球是否全部被覆盖 | 相对871新增拦截 | 相对871新增放行 |
| ---: | --- | ---: | ---: |
| 871 | 是 | 0 / 1280 | 0 / 1280 |
| 512 | 是 | 8 / 1280 | 0 / 1280 |
| 256 | 是 | 11 / 1280 | 0 / 1280 |

合并球变大后会多挡住一些原先放行的状态。当前五个场景的选中抓法保持，不代表更多场景的可行解都能保持。

## 下一步

保留871球，优先优化重复配置处理：机器人静态参数、球参数与当前场景在内存中保存，候选开度变化时只更新必要数据；完整配置留档与规划计算分开。此前“只更新开度”的完整对照未提速，本次应针对剖析明确指出的YAML往返、碰撞世界重复装载和接触几何排序逐项验证。

球数精简放在这几项之后考虑。少球的GPU收益存在，但本轮已经显示512球继续减半未再降低完整请求耗时。
