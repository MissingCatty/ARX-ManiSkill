# V8规划加速方法调研

建议以已经启用的双臂交替搜索为起点，先验证原生批量IK，再比较几何IK和地图关节解复用。可达性地图作为加速工具，是否保留由总耗时决定。当前重点是合并大量小规模求解，并减少同一场景的重复绑定。

## 现有证据

交替搜索已经解决“右臂扫描到底，左臂很晚才参与”的问题。香蕉同卡回放428.23→8.55秒的结果归入V3。V8所有分组都使用优化后的交替搜索作为对照。

交替优化前的65个配对规划场景中，GraspGenX两臂合计检查12452次终点：

| 候选检查结果 | 次数 | 占全部检查 |
| --- | ---: | ---: |
| 当次求解未得到运动学解 | 10878 | 87.4% |
| 得到解，碰撞检查未通过 | 1447 | 11.6% |
| 通过终点，继续后续动作检查 | 127 | 1.0% |

这说明成批处理IK值得优先验证。地图缓存主要帮助找到已有解；地图没有覆盖时，仍需求解。现行交替搜索的全69份观测耗时将在V8回放中重新测量。历史数据源为`tmp/latency_analysis/v6_final_20261126_01/analysis.json`。

## 方法比较

| 方法 | 参考方法的做法 | 对本项目的用法 | 优先级 |
| --- | --- | --- | --- |
| cuRobo批量IK | GPU并行处理多个目标及初值 | 一个候选占一个批次行，成批产生解，再按原排名检查路径 | 第一优先 |
| IK-Geo / EAIK | 利用相交轴、平行轴分解六轴IK | 为原目标产生多个关节分支，独立FK与限位核验后使用原碰撞检查 | 优先验证适配 |
| MoveIt Cached IK | 邻近缓存解作初值，失败回到原初值 | 比较现有地图和成功解缓存的查询成本与求解收益 | 独立对照 |
| VAMP / VAMP-MR | 对FK和碰撞检查进行向量化 | 后续借鉴数据常驻与成批检查方式；不属于B、C、D已实施模块 | 尚未实施 |

cuRobo官方实现提供`max_batch_size`、`seed_config`和逐行批量结果。MoveIt采用“缓存初值→原初值回退”；其文档也指出，对本身很快的UR解析IK示例，缓存会增加开销。[cuRobo官方实现](https://github.com/NVlabs/curobo/blob/main/curobo/_src/solver/solver_ik.py)、[MoveIt官方文档](https://moveit.picknik.ai/main/doc/examples/kinematics_configuration/kinematics_configuration_tutorial.html)。

IK-Geo将三平行轴等六轴家族化成几何子问题；EAIK进一步自动识别结构，提供URDF、齐次变换输入与C++/Python接口，也支持CPU批处理。[IK-Geo](https://github.com/rpiRobotics/ik-geo)、[EAIK项目主页](https://ostermd.github.io/EAIK/)。VAMP-MR将批量FK和碰撞检查组织为CPU SIMD操作，可借鉴其实现方式。[VAMP-MR项目主页](https://vamp-mr.github.io/vamp-mr/)。

## ARX静态几何核查

本轮读取当前URDF，把六个转轴变换到同一零位坐标系：

| 关节 | 零位转轴方向，忽略浮点尾差 |
| --- | --- |
| right_joint21 | Z方向 |
| right_joint22 | Y方向 |
| right_joint23 | 负Y方向 |
| right_joint24 | Y方向 |
| right_joint25 | 负Z方向 |
| right_joint26 | 负X方向 |

22/23/24轴最大叉积范数2.45×10⁻¹⁶，25/26轴线距离约1.39×10⁻¹⁷米。这支持把ARX作为“三个连续平行转轴”家族的适配候选。EAIK实际识别、求解与计时仍待验证；静态几何核查阶段未执行IK。

部分关节限位跨过π。几何解应枚举满足原限位的2π等价表示，再独立复算原EEF目标；数值裁剪不能替代等价分支转换。最小二乘输出也按原2毫米、0.03弧度门槛验收，无合格解时调用原IK，保留工作空间边界的原容差含义。

## 本地接口核查

| 位置 | 当前情况 | V8接法 |
| --- | --- | --- |
| `fingertip_contact/planning.py` | 纯运动学辅助求解器为`max_batch_size=1` | 新建并预热16、32目标的独立批量求解器 |
| 本地`solver_ik.py` | 支持批次补齐、输入种子和多分支返回 | 原候选占独立行，保留编号与有效行掩码 |
| LM初值阶段 | 输入种子先经过LM，再进入优化 | 记录地图/几何种子的真实流向与数量 |
| `resident_planner.py` | 每次绑定更新世界、重置搜索状态 | 比较同一请求内按臂复用上下文的时间与显存 |
| `CapabilityMap.query_pose` | 单次取8192个位置邻居再筛旋转 | 测量分块批量查询和返回集合大小 |
| `OrientationIndex` | 重力方向索引用于允许底盘转向的必要条件筛选 | 固定站位查询加入完整SO(3)旋转比较 |
| `witness_pool.py` | 支持单个精确目标的见证复用 | 按候选编号管理多个分支 |

16/64是左右臂调度窗口，16/32是GPU求解批量，两者分别记录。各方法保持同一左右臂调度。批量求解每行保留自己的结果，路径阶段仍按原评分推进；把多个抓法混入由内部代价选优的goalset会改变选择规则，因此本版采用逐行批次接口。

批量接口同时覆盖现有的完整场景IK与纯运动学回退。后者继续执行独立FK、限位、非桌面碰撞和V2局部指尖检查，保留当前近桌抓取的处理方式。

## 地图的接入判断

现有约1056万组见证先测直接命中率、近邻初值收益和查询成本。5毫米位置统计格不能代表2毫米、0.03弧度条件下的完整六维覆盖。

查询结果达到原目标容差时进入当前场景碰撞检查；近邻作为原目标的初值，缺少记录时调用现有IK。左右臂、body4、TCP43和安装变换使用已验证接口，保留完整旋转和多个关节分支。首轮缓存冻结，在线增加成功记录的效果另组测量。

## 实施顺序

| 顺序 | 工作 | 要回答的问题 |
| --- | --- | --- |
| 1 | 冻结现行交替搜索，建立分项计时 | 现阶段IK、碰撞、绑定与路径各花多少时间 |
| 2 | 接原生批量IK，比较16、32目标 | 保持每目标预算时，成批处理节省多少总时间 |
| 3 | 单独比较按臂复用上下文 | 重绑定能省多少，需要增加多少显存 |
| 4 | 独立环境适配EAIK/IK-Geo | ARX能否直接用几何分解，多分支是否有收益 |
| 5 | 单独接地图见证与初值 | 查询和回退合计是否更快 |
| 6 | 组合有效模块，回放全部69份观测 | 中位数、P90与规划通过率是否共同改善 |

各组同卡、统一预热、交替先后顺序；短时计时多次重复，模型、场景物理、原抓姿和评分沿用冻结版本。调研后的原生批量适配已启动五份观测×三组纯规划预检。几何IK、绑定复用与地图分组继续按本表顺序推进，物理抓取预算0。
