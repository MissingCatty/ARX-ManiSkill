# 双臂候选交替搜索

本次优化针对双臂规划中的等待时间。V6稀疏香蕉场景中，右臂检查3320个候选耗时444.78秒，左臂随后检查第一个候选就通过，整次首次规划耗时449.77秒。

## 搜索怎样调整

| 环节 | 原搜索 | 交替搜索 |
| --- | --- | --- |
| 搜索顺序 | 先完成右臂搜索，再开始左臂 | 右臂检查一批，左臂检查一批，再继续下一批 |
| 每批数量 | 一次请求可遍历完整候选池 | 首轮每臂最多16个，之后每批最多64个 |
| 搜索进度 | 每只手只接收一次候选池 | 各臂保存游标，从上次停下的候选继续 |
| 找到可执行候选后 | 限制后搜索手臂的候选前缀 | 两臂都受当前最佳原始名次约束，仍检查同名次候选 |
| 选择结果 | 原始候选名次优先，同名次比较关节位移，再优先右臂 | 沿用同一规则 |
| 候选交接 | 一次解码，双臂共享对象 | 保持一次解码，每批仅建立共享对象引用的列表视图 |

例如两臂都尚未找到解时，先检查右臂第1–16个候选，再检查左臂第1–16个。若左臂第1个候选通过，右臂此前已检查过同名次，便可结束比较。若两臂都没有通过，则分别从第17个继续，之后每批扩大为64个，以减少两臂状态重绑定次数。只剩一臂需要继续时，直接检查其剩余竞争前缀。

每个窗口都调用现有单臂规划器，保留抓取终点、预抓取与抬升终点、完整路径和局部接近检查。各臂开爪检查仍沿用原实现，碰撞模型保持每臂871球、TCP43和V2指尖规则。

每次请求保存`interleaved_search.json`，记录两臂各窗口的原始起止索引、检查次数、当前最佳名次和耗时。每个窗口的独立回执位于`arms/<arm>/search_windows/`，各臂最终结果汇总此前窗口的全部候选事件和拒绝计数。

临时窗口结束后恢复完整候选视图；窗口内部的局部索引转换回原候选池索引。后续执行继续读取选中臂的同一抓取方案。
