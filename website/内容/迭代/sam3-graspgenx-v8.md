## 本版进度

V8「可达性索引与批量IK加速」已建立，承接V4，与V7候选后处理并列。问题定位与实验方案已完成，接下来实现查询和规划适配。当前本版规划回放0次、物理抓取0次。

## 要解决什么问题

GraspGenX通常会给出数千个抓法。当前程序按评分顺序检查，先找机械臂关节解、检查碰撞，再尝试运动路径。遇到一串难以求解的候选时，会反复运行IK搜索。

已有可达性地图保存约1056万组关节解，记录了末端能到的位置和朝向。V8把它用成查询库：先找到可复用的关节解，减少重新计算。

此前31个配对场景的GraspGenX组，两臂合计产生5444次抓取终点检查。下表是本版方案登记时的问题定位数据。

| 抓取终点检查结果 | 次数 | 比例 |
| --- | ---: | ---: |
| 当次IK未找到运动学解 | 4635 | 85.1% |
| 有运动学解，被碰撞检查拒绝 | 750 | 13.8% |
| 通过抓取终点检查，继续检查后续动作 | 59 | 1.1% |

## 怎样借鉴数据库

| 步骤 | 具体怎么做 | 目的 |
| --- | --- | --- |
| 1. 建立索引 | 按手臂、位置和完整朝向查询，关联正确的机器人与TCP配置 | 快速找到相关记录 |
| 2. 批量查询 | 一批抓法一起取回邻近关节解，索引常驻内存 | 减少逐个查询的开销 |
| 3. 复用关节解 | 复算末端位置和朝向、核对关节限位，达到原门槛后检查当前场景碰撞 | 减少重复IK计算 |
| 4. 用邻近解帮助IK | 邻近记录作为初值，继续求解到原来的抓取位姿 | 提高求解效率 |
| 5. 分批检查 | 比较每批16、32个候选，保持原评分顺序，找到可执行方案就停止 | 减少后续无用计算 |
| 6. 保存有效解 | 持久保存已验证的运动学解，当前场景碰撞重新检查 | 复用已有计算结果 |

地图没查到的抓法继续交给原IK。一个关节解碰撞时，继续检查其他关节分支。抓取位姿、原评分和候选顺序保持不变。

## 本版链路

头部RGB-D → SAM3 → RaySt3R → GraspGenX原候选 → 可达性索引查询与关节解复用 → 分批IK和终点碰撞检查 → 按原评分做cuRobo路径规划 → 选臂抓取。

底盘与升降站位、每臂871球、TCP43、指尖最前端10毫米的2毫米桌面余量沿用当前配置。

## 准备比较哪些方案

| 分组 | 相比原实现的变化 | 当前进度 |
| --- | --- | --- |
| 原实现对照 | 原顺序逐候选检查 | 已有实现，待配对回放 |
| 索引复用 | 查询并复用关节解，邻近解辅助IK | 待实现 |
| 索引复用＋分批检查 | 在索引复用基础上批量检查候选终点 | 待实现与比较批大小 |

先使用同一套69份有效观测和保存候选做规划回放，保持相同站位、物体状态与场景。共同站位失败的5例在74例总体范围中保留，SAM3最终失败单列剔除。物理抓取批次在回放结果出来后确定。

## 怎样判断有没有改善

| 要看什么 | 具体记录 |
| --- | --- |
| 查表值不值得 | 查询耗时、命中率、直接复用关节解的数量 |
| 是否减少重复计算 | IK调用、初值数量、终点碰撞检查和路径规划调用数 |
| 总体是否更快 | 查询、IK、碰撞和路径合计的中位数、P90及样本数 |
| 规划效果是否保住 | 同场景规划通过率、选中抓法与手臂变化、失败阶段 |
| 后续实际抓取效果 | 正式验证中的抓取成功率与视频 |

计时采用同卡、统一预热和相同输入，分别记录加载、查询、IK、碰撞与路径耗时。
