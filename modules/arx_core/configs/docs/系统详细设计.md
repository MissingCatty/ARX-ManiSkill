# CoolAS ARX 系统设计

本文档说明 `/home/arx/coolas-arx` 当前项目结构、各目录职责、文件放置标准，以及后续维护时的修改规范。

目标是让后续开发时能快速判断：

- 新代码应该放在哪里；
- 哪些目录是正式运行路径；
- 哪些目录只用于兼容、实验或测试；
- 修改某个功能时应该优先改哪些文件。



本文档同时包含系统设计说明和代码结构说明。前半部分描述系统架构、模块边界、数据流、控制流、资源互斥和扩展方式；后半部分保留原有代码结构手册内容，用于指导后续维护和修改。

# 第一部分：系统设计

## 1. 设计目标

`coolas-arx` 的目标是把原先集中在大脚本中的 ZeroGrasp + LangSAM + ARX 实机抓取流程，拆分为可维护、可测试、可组合的服务化系统。

核心设计目标：

- 将视觉分割、抓取推理、机器人执行拆成独立模块；
- 将真实机器人硬件访问集中到 `arx-ops`；
- 将抓取任务编排集中到 `zerograsp` 服务；
- 保留 legacy 代码用于对照和兼容，但不作为正式主路径；
- 用统一 schema 管理 API 请求和响应；
- 用配置文件管理路径、阈值、速度、topic、CAN 资源等可变参数；
- 让每个模块既能通过 HTTP 调用，也能通过 Python 函数直接调用。

## 2. 系统总体架构

当前系统由抓取闭环服务、底盘语义建图/导航模块和一组共享基础设施组成：

```text
用户 / 上层程序
  |
  | HTTP
  v
zerograsp 服务 :8003
  | 负责完整抓取任务编排
  |
  |-- HTTP --> arx-ops 服务 :8001
  |             负责相机、机械臂、夹爪、底盘升降、底盘移动
  |
  |-- HTTP --> langsam 服务 :8002
  |             负责图像分割
  |
  |-- subprocess --> ZeroGrasp 模型代码
                负责抓取候选生成

DualMap 模块
  | 负责底盘语义建图、前沿探索、语义导航
  |
  |-- HTTP --> arx-ops 服务 :8001
                负责 RGB-D 采集和底盘移动执行
```

主抓取流程：

```text
POST /task/run-grasp
  -> arx-ops /camera/capture-rgbd
  -> arx-ops /arm/status
  -> langsam /segment
  -> zerograsp model subprocess
  -> zerograsp planning
  -> optional arx-ops /arm/move-end-pose
```

服务之间通过 HTTP 通信，不直接互相 import 硬件或模型内部实现。共享的数据结构放在 `shared/arx_shared/schemas.py`。

## 3. 模块划分

### 3.1 arx-ops

职责：真实机器人操作与实机流程支持。

主要能力：

- 读取机械臂 `/arm_status`；
- 控制机械臂末端位姿；
- 机械臂回 home；
- 夹爪打开/闭合；
- RealSense RGB-D 采集；
- 底盘升降；
- 底盘移动；
- 通过统一 body controller 合并 CAN5 上的 lift/move 命令。

设计原则：

- 所有真实硬件副作用集中在这里；
- 对外提供 HTTP API；
- 对内提供函数式接口；
- 能把上层语义请求翻译成 ROS、SDK、C++ 工具或 legacy slow move 调用。

### 3.2 langsam

职责：目标分割服务。

主要能力：

- 接收 RGB 图像路径和 prompt；
- 使用 LangSAM 生成 mask；
- 支持 HSV 分割作为轻量替代；
- 输出 mask、overlay 和 JSON 信息。

设计原则：

- 只负责分割，不负责抓取规划；
- 不直接访问机器人；
- 输出文件路径由请求或 storage 工具统一管理。

### 3.3 zerograsp

职责：抓取推理、抓取规划和任务编排。

主要能力：

- 准备 ZeroGrasp 输入；
- 调用 ZeroGrasp 模型；
- 读取推荐抓取结果；
- 做相机坐标到 ARX 末端坐标的转换；
- 做安全范围检查；
- 编排完整 `/task/run-grasp` 流程。

设计原则：

- `orchestrator.py` 只负责流程编排；
- `planning.py` 负责几何转换和安全检查；
- `model.py` 负责模型子进程边界；
- 不直接 import ROS、RealSense、ARX message。

### 3.4 shared

职责：跨服务共享基础设施。

包含：

- API schema；
- 配置读取；
- 文件工具；
- 几何工具。

设计原则：

- `shared` 只能放纯通用逻辑；
- 不能依赖具体服务；
- 不能包含硬件副作用。

### 3.5 DualMap

职责：底盘侧语义建图、前沿探索和语义导航。

主要能力：

- 通过 RGB-D/Odom 输入维护 local_map 和 global_map；
- 将稳定低移动性对象提升到全局语义地图；
- 基于 layout/wall、语义对象和 RGB-D 端点构建 frontier occupancy grid；
- 规划到语义目标候选区域的路径；
- 导航过程中持续更新 local_map，并在 global anchor 附近二次确认局部目标。
- 通过 brain_agent 的 `dualmap_map_status`、`dualmap_explore`、`dualmap_semantic_navigation` 三个 Task Operator 暴露地图检查、探索和语义导航边界；
- 语义导航成功必须由终点 RGB 图像确认查询目标在视野中且语义匹配，不能只采用路径或 Runner 状态。

设计原则：

- 算法主体保留在 `servers/DualMap/dualmap` 和 `servers/DualMap/utils`；
- COOLAS 适配逻辑放在 `servers/DualMap/coolas_dualmap`；
- 实机副作用通过 `arx-ops` HTTP API 完成，不直接持有相机、底盘或 CAN；
- 原 Hydra/CLI 入口保持兼容，旧论文离线 runner 不作为当前大小脑协同主路径。
- 长程大脑只拆解“到取物处—抓取—到放置处—放置”阶段；具体地图检查、无图探索、导航、抓放和评估均由小脑按 Operator 边界调配。

## 4. 服务边界

### 4.1 HTTP 边界

所有跨服务调用都通过 HTTP 完成：

```text
zerograsp -> arx-ops
zerograsp -> langsam
DualMap -> arx-ops
```

这样做的好处：

- 分割服务可以独立重启；
- 机器人控制服务可以独立调试；
- ZeroGrasp 推理和机器人硬件隔离；
- 每个服务可单独做 health check。

### 4.2 函数边界

每个 API 路由都是薄封装，对应内部函数。例如：

```text
POST /arm/home -> coolas_arx_client.motion.home_arm
POST /segment -> coolas_langsam.segment.segment_image
POST /task/run-grasp -> coolas_zerograsp.orchestrator.run_grasp_task
```

这样可以在不启动 HTTP 服务时直接做函数级测试。

### 4.3 子进程边界

以下能力通过子进程调用外部程序：

- ZeroGrasp 模型推理；
- LangSAM legacy infer；
- ARX slow move 控制脚本；
- direct lift C++ 工具；
- chassis runner ROS 发布脚本。

子进程边界的好处是可以复用原项目和外部环境；代价是需要认真处理 timeout、stdout/stderr、进程退出和资源释放。

```text
        |

```

每次 `/task/run-grasp` 都会生成独立 run 目录，典型结构：

```text
runs/zerograsp_task_xxx/
├── camera/
├── zg_input/
├── zg_output/
└── run_report.json
```

### 5.2 状态数据流

机械臂状态来源：

```text
ARX ROS controller -> /arm_status -> arx-ops /arm/status -> zerograsp planning
```

底盘状态来源：

```text
tools/unified_body_controller -> Unix Socket 状态 -> arx-ops /chassis/status 或 /lift/status
```

底盘语义地图数据来源：

```text
arx-ops /camera/capture-rgbd 或 ROS RGB-D/Odom
  -> DualMap local_map
  -> DualMap global_map
  -> frontier occupancy_grid
  -> semantic navigation action_path
  -> arx-ops /chassis/move
```

## 6. 控制流设计

### 6.1 机械臂运动

机械臂运动 API 最终调用：

```text
legacy/scripts/slow_move_end_pose_v2.py
```

当前它仍是底层 ROS `RobotCmd` 发布者。`arx-ops/motion.py` 负责把 HTTP 参数转换为 CLI 参数，并处理 timeout、返回值和错误信息。

典型模式：

- `/arm/move-end-pose`：移动到目标位姿；
- `/gripper/open`：固定时长发布打开命令；
- `/gripper/close`：固定时长发布闭合命令；
- `/arm/home`：先闭合夹爪，再执行 q-style home。

### 6.2 抓取执行

`/task/run-grasp` 当前只负责执行最终抓取 motion，不自动 home。

抓取后带物返回需要显式调用：

```text
POST /arm/home?close_gripper=true
```

这个设计让抓取和返回解耦，便于调试和人工确认。

### 6.3 底盘升降和移动

底盘升降和移动统一使用：

```text
HTTP API: lift.py / chassis.py
  ↓ Unix Socket: /tmp/coolas_body_control.sock
tools/unified_body_controller（唯一持有 can5）
  ↓ 同一 400 Hz 循环
SDK setHeight() + setChassisCmd() + loop()
```

`direct_lift_height_dynamic` 仅保留为离线诊断工具，正常 API 不再启动它。

## 7. CAN5 统一控制设计

### 7.1 CAN 资源

| 资源 | 使用方 | 说明 |
|---|---|---|
| `can3` | ARX 机械臂控制器 | 机械臂、夹爪 |
| `can5` | `tools/unified_body_controller` | 平台升降和底盘移动的唯一 CAN5 持有者 |

### 7.2 合并控制原则

- `/lift/height` 只更新 C++ 控制器中的 SDK 原生高度目标；
- `/chassis/move` 只更新速度和运动截止时间；
- C++ 控制器在同一 400 Hz 循环中调用 SDK 的高度、底盘和 `loop()` 接口；
- `/chassis/stop` 清零速度但保留高度目标；
- `/lift/stop` 将当前 `height_command` 冻结为新目标并持续发布；
- 检测到遗留 direct lift 进程时拒绝启动统一控制器，避免两个进程同时写 CAN5。

### 7.3 高度控制状态机

`height`、`feedback_height`、`target_height`、`height_command` 均为厂商 SDK 原生量，不是厘米。收到新目标后，控制器根据 `target_height - feedback_height` 计算外环输出，再通过 `ramp_step` 限制每周期命令变化。反馈误差进入 `feedback_tolerance` 后设置 `height_reached=true`，冻结最后的 `height_command` 并持续调用 `setHeight()`，用于承重保持。

移动状态与高度状态互相独立：移动截止时间到达时只清零 `linear_x/linear_y/angular_z`，不会清除平台目标或停止高度控制。因此移动、升降和 hold 可同时进行。

### 7.4 生命周期与启动

`scripts/init_client.sh` 是统一控制器的启动入口。它清理遗留 CAN5 进程，等待 `can3/can5`，在二进制不存在时执行 `tools/build_unified_body_controller.sh`，启动控制器，并等待 Socket 返回有效 `feedback_height`。API 不负责懒启动，初始化脚本需要在服务运行期间保持常驻。

## 8. 配置设计

配置文件集中放在：

```text
configs/
```

主要配置：

| 文件 | 说明 |
|---|---|
| `arx.yaml` | 机器人、相机、机械臂、夹爪、lift、chassis 配置 |
| `zerograsp.yaml` | ZeroGrasp 模型路径、checkpoint、任务参数、安全阈值 |
| `langsam.yaml` | LangSAM/SAM/GroundingDINO 配置 |
| `calibration.yaml` | 坐标变换和标定矩阵 |
| `services.yaml` | 三个服务的 URL |

设计原则：

- 环境相关路径放配置；
- 安全阈值放配置；
- 速度、timeout、默认高度、夹爪开合值应配置化；
- 不要把实机绝对路径散落到业务逻辑中。

## 9. 错误处理设计

### 9.1 HTTP 层

API 通常返回结构化对象。机器人执行类接口多返回 `ExecutionResult`：

```json
{
  "ok": false,
  "message": "...",
  "command": [...],
  "returncode": null,
  "data": {}
}
```

### 9.2 子进程层

子进程调用应保留：

- 实际命令 `command`；
- 退出码 `returncode`；
- stdout/stderr 摘要；
- timeout 信息；
- 关键运行数据。

### 9.3 实机错误

常见实机错误包括：

- `/arm_status` 无发布；
- CAN 口未初始化；
- `can5` 模式冲突；
- 机械臂目标超出安全范围；
- ZeroGrasp 没有生成推荐抓取；
- 分割找不到目标。

这些错误应尽量在 API 返回中说明具体检查方向。

## 10. 扩展设计

### 10.1 新增机器人能力

新增机器人操作时：

1. 在 `arx-ops/coolas_arx_client/` 中实现函数；
2. 如需 API，加入 `api.py`；
3. 如需请求模型，加入 `shared/arx_shared/schemas.py`；
4. 如需默认参数，加入 `configs/arx.yaml`；
5. 更新 `docs/API说明手册.md`。

### 10.2 新增分割方法

新增分割方法时：

1. 扩展 `SegmentRequest.method`；
2. 在 `servers/langsam/coolas_langsam/segment.py` 中实现；
3. 如需模型路径，加入 `configs/langsam.yaml`；
4. 更新 API 文档。

### 10.3 新增抓取规划策略

新增抓取规划策略时：

1. 在 `servers/zerograsp/coolas_zerograsp/planning.py` 中实现；
2. 必要时扩展 `GraspPlanRequest`；
3. 安全检查必须保留；
4. 更新 `zerograsp.yaml` 和 API 文档。

### 10.4 新增完整任务流程

如果新增不同的任务编排，例如放置、搬运、多物体抓取，应优先新增 orchestrator 函数，而不是继续扩大单个函数：

```text
coolas_zerograsp/orchestrator.py
```

必要时可以拆成：

```text
orchestrators/grasp.py
orchestrators/pick_place.py
```

## 11. 当前已知设计取舍

### 11.1 保留 legacy slow move

当前机械臂底层控制仍复用 `legacy/scripts/slow_move_end_pose_v2.py`。这样做的好处是稳定、贴近已验证实机行为；缺点是它仍是 CLI/子进程边界，不是纯 Python 控制模块。

后续如果要继续重构，可以把 slow move 的 ROS publisher 逻辑迁移到 `arx-ops/coolas_arx_client/motion_runner.py` 或类似模块。

### 11.2 `/task/run-grasp` 不自动 home

当前抓取和返回分离：

- `/task/run-grasp` 负责抓取 motion；
- `/arm/home` 负责返回 home。

这样便于调试，也避免抓取后未经确认就自动移动。后续如果需要一键完整流程，可以在 `/task/run-grasp` 新增可选参数，例如 `return_home=true`。

### 11.3 lift 和 chassis 统一控制

当前通过常驻 body controller 在同一控制周期下发高度和底盘速度。移动停止后只清零速度，高度闭环继续运行并 hold 当前目标。

## 12. 总体结构

当前项目根目录主要结构如下：

```text
coolas-arx/
├── README.md
├── requirements.txt
├── arx-ops/
├── servers/
│   ├── langsam/

├── configs/
├── scripts/
├── tasks/
├── tools/
├── legacy/
├── test/
```

按职责可分为：

| 类别 | 目录 | 说明 |
|---|---|---|

| 运行产物 | `runs/` | 每次任务输出，不应作为源码维护 |

## 13. 正式运行路径

当前 phase2 主流程是服务化路径：

```text
zerograsp server POST /task/run-grasp
  -> arx-ops POST /camera/capture-rgbd
  -> arx-ops GET /arm/status
  -> langsam server POST /segment
  -> zerograsp model subprocess
  -> zerograsp planning
  -> optional arx-ops POST /arm/move-end-pose
```

正式入口包括：

```text
scripts/run_arx_client.sh
scripts/run_langsam_server.sh
scripts/run_zerograsp_server.sh
scripts/init_client.sh
```

说明：虽然脚本名里仍保留 `run_arx_client.sh`，但服务目录已经改为 `arx-ops/`。保留脚本名是为了避免改变已有操作习惯。

## 14. 根目录文件

### `README.md`

项目总说明。应该包含：

- 项目用途；
- 服务启动方法；
- 实机初始化方法；
- 关键 API 示例；
- 安全注意事项。

不建议把过长 API 细节全部写在 README，详细 API 应放到：

```text
PyYAML

```

注意：ZeroGrasp、LangSAM、ROS、RealSense 等较重依赖通常由已有 conda 环境或外部 SDK 提供，不一定全部写入该文件。

## 15. `arx-ops/`

### 目录职责

`arx-ops/` 是真实机器人操作服务目录。它负责：

- 机械臂状态读取；
- 机械臂末端控制；
- 机械臂 home；
- 夹爪打开/闭合；
- RealSense RGB-D 采集；
- 底盘统一升降控制；
- 底盘移动；
- CAN5 单进程统一控制。

它不是单纯硬件 gateway，后续也可以放与机器人实机运行相关的操作编排代码。

### 当前结构

```text
arx-ops/
├── app.py
├── README.md
└── coolas_arx_client/
    ├── __init__.py
    ├── api.py
    ├── body_mode.py
    ├── camera.py
    ├── chassis.py
    ├── chassis_runner.py
    ├── lift.py
    ├── motion.py
    └── robot.py
```

### 文件职责

| 文件 | 职责 |
|---|---|
| `app.py` | uvicorn 入口，导出 FastAPI `app` |
| `coolas_arx_client/api.py` | HTTP 路由定义，尽量保持薄封装 |
| `coolas_arx_client/robot.py` | ROS 环境、`/arm_status` 读取、ARX workspace setup 路径 |
| `coolas_arx_client/motion.py` | 机械臂末端移动、home、夹爪控制 |
| `coolas_arx_client/camera.py` | RealSense RGB-D 采集 |
| `coolas_arx_client/lift.py` | 通过 Unix Socket 更新统一 C++ 控制器的高度目标 |
| `coolas_arx_client/chassis.py` | 底盘移动 API 逻辑 |
| `coolas_arx_client/body_control.py` | 统一 C++ 控制器的 Unix Socket 客户端 |
| `coolas_arx_client/body_mode.py` | 统一 C++ 控制器健康检查及遗留 direct lift 冲突检测 |
| `tools/unified_body_controller.cpp` | 独占 CAN5，合并高度与底盘速度并执行 SDK 控制循环 |

### 维护规范

- HTTP 路由只放在 `api.py`。
- 业务逻辑不要直接写在 `api.py`，应放到对应模块函数中。
- 新增机器人操作 API 时，优先新增或扩展 `motion.py`、`lift.py`、`chassis.py`、`camera.py` 等模块。
- 涉及请求/响应字段时，先修改 `shared/arx_shared/schemas.py`。
- 涉及默认值时，优先放入 `configs/arx.yaml`。
- 不要在 `arx-ops/` 中直接写一次性测试脚本；测试脚本放 `scripts/` 或 `test/`。

## 16. `servers/`

图像分割服务。当前支持：

- HSV 分割；
- mask、overlay、info JSON 输出。

```text
servers/langsam/

    ├── __init__.py
```

### 文件职责

- 将相机坐标抓取转换到 ARX 末端坐标；
- 做安全检查；
- 编排完整抓取任务 `/task/run-grasp`。

### 当前结构

```text
servers/zerograsp/
├── app.py
├── README.md
├── coolas_zerograsp/
│   ├── __init__.py
│   ├── api.py
│   ├── grasp.py
│   ├── model.py
│   ├── orchestrator.py
│   ├── planning.py
│   └── storage.py
└── vendor/
```

### 文件职责

| 文件/目录 | 职责 |
|---|---|
| `app.py` | uvicorn 入口 |
| `coolas_zerograsp/api.py` | `/health`、`/grasp/predict`、`/grasp/plan`、`/task/run-grasp` 路由 |
| `coolas_zerograsp/grasp.py` | 抓取推理 API 的轻量封装 |
| `coolas_zerograsp/model.py` | 调用 ZeroGrasp 模型子进程、读取推理输出 |
| `coolas_zerograsp/planning.py` | 坐标变换、抓取位姿规划、安全检查 |
| `coolas_zerograsp/orchestrator.py` | 完整任务编排：采集、分割、推理、规划、可选执行 |

| `vendor/` | vendored ZeroGrasp 最小运行代码，不作为主要业务开发目录 |

### 维护规范

- `/task/run-grasp` 的流程改动放 `orchestrator.py`。
- 坐标变换和安全边界改动放 `planning.py`。
- ZeroGrasp 子进程命令、checkpoint、config 相关逻辑放 `model.py`。
- 不要在 `orchestrator.py` 里直接写复杂几何计算。
- 不要直接修改 `vendor/`，除非明确是在修复 vendored ZeroGrasp 兼容问题。

| `files.py` | 通用文件/目录工具 |

### 维护规范

- 新增 API 字段时，先改 `schemas.py`。
- 跨服务复用的纯函数可以放 `shared/`。
- 不要在 `shared/` 中 import `coolas_arx_client`、`coolas_langsam`、`coolas_zerograsp`。

## 24. `tasks/`

### 目录职责

典型内容：

```text

├── README.md
├── common/
├── grasp/
├── lift/
├── chassis/
└── examples/
```

### 维护规范

- 任务脚本通过 HTTP API 调用正式服务，不直接发布 ROS topic。
- 任务脚本只做流程编排，不复制底层控制、分割、抓取推理逻辑。
- 实机执行脚本必须显式说明会调用哪些 API，以及是否会触发机器人运动。
- 运行输出写入 `runs/`，不要写入 `tasks/`。
- 稳定任务如果需要对外服务化，再迁移为正式 API。

## 28. 新增代码放置规则

### 新增 HTTP API

| API 类型 | 应放目录 |
|---|---|
| 机器人操作、硬件相关 | `arx-ops/coolas_arx_client/` |
| 图像分割 | `servers/langsam/coolas_langsam/` |
| 抓取推理、规划、任务编排 | `servers/zerograsp/coolas_zerograsp/` |
| 跨服务 schema | `shared/arx_shared/schemas.py` |
| 跨服务纯函数 | `shared/arx_shared/` |

新增 API 的基本步骤：

1. 在 `shared/arx_shared/schemas.py` 增加请求/响应模型。
2. 在对应服务模块中实现函数。
3. 在对应 `api.py` 中增加 FastAPI 路由。
4. 如有默认参数，写入 `configs/`。
5. 更新 `docs/API说明手册.md`。
6. 补充测试或测试流程文档。

### 新增启动脚本

放入：

```text
scripts/
```

要求：

- 使用 `#!/usr/bin/env bash`；
- 使用 `set -euo pipefail`；
- 自动计算项目根目录：

```bash
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
```

### 新增底层工具

放入：

```text
tools/
```

如果工具属于某个具体方向，建议建立子目录：

```text
tools/lift/
tools/can/
tools/calibration/
```

## 29. 命名规范

### 服务和目录命名

- 服务目录使用职责命名，例如 `arx-ops`、`langsam`、`zerograsp`。
- Python 包使用 `coolas_*` 前缀，例如 `coolas_arx_client`、`coolas_langsam`、`coolas_zerograsp`。
- 历史原因：`coolas_arx_client` 包名暂时保留，不随外层目录 `arx-ops` 改名。

### 文件命名

- Python 文件使用小写加下划线：`body_mode.py`。
- Shell 脚本使用动作前缀：`run_*`、`stop_*`、`init_*`。
- 文档文件名应表达用途，例如 `API说明手册.md`、`代码结构手册.md`。

### API 命名

- 资源名使用名词：`/arm`、`/gripper`、`/lift`、`/chassis`。
- 动作使用清晰动词：`/arm/home`、`/lift/stop`、`/task/run-grasp`。
- 不建议新增含糊接口名，例如 `/run`、`/do`、`/control`。

## 31. 当前维护边界总结

- 正式服务主路径：`arx-ops/`、`servers/langsam/`、`servers/zerograsp/`。
- 公共模型和工具：`shared/`。
- 配置：`configs/`。
- 用户可执行脚本：`scripts/`。
- 本地底层工具：`tools/`。
- 旧逻辑仅作参考：`legacy/`。
- 运行产物不作为源码：`runs/`。

以后维护时，应尽量让 API 层保持薄封装，业务逻辑留在对应模块，跨服务模型统一放在 `shared/`，实机路径和阈值参数优先配置化。
