# 候选数据交接与后台留档

抓取候选在生成后直接通过共享内存交给双臂规划器，候选文件同时由后台线程保存。规划端只解码一次，两臂共享同一个有序候选池；第二臂的搜索前缀是内存视图，不复制整份候选文件。

## 数据怎样流动

1. 生成器或控制器调用 `arx_project.artifacts.publish_candidate_pool`，创建带校验值的共享内存，并提交后台保存任务。
2. RPC 只传共享内存名称、长度、校验值和本次观测标识。完整候选不经过大型 JSON 消息，也不等待文件保存完成。
3. 规划器进入 `candidate_scope`，解码一次候选。左右臂绑定同一数据，按原有评分顺序、第二臂前缀和原碰撞规则计算。
4. 请求计算完成后，规划端确认自己的记录已保存；客户端再确认生成端的候选快照已保存，释放共享内存。后台保存失败会向上传播，调用端不能把这次请求标为正常完成。

当前数据中的标签、协议名称和数值不进入旧路径转换。历史文件中的真实旧路径仍按原映射读取，兼容旧实验资料。

## 保存哪些文件

| 文件 | 内容 |
| --- | --- |
| `candidates/candidate_pool.json` | 每次观测的一份完整候选，保留原位姿、评分和顺序 |
| `arms/<arm>/candidates/candidate_pool_reference.json` | 对应完整候选的来源、校验值和该臂使用的前缀长度 |
| `candidate_io.json` | 候选来源、解码次数、访问次数及加载耗时 |
| `candidate_snapshot_commit.json` | 后台快照已完成的确认记录 |

读取每臂候选使用 `modules.curobo.candidate_io.store.read_snapshot`，它同时支持旧完整文件和新引用记录。旧的 `graspcl/candidate_pool.json` 路径继续支持。

支持共享内存的规划器在 `configs/modules.json` 登记 `candidate_transport_format`。旧文件消费者保留原接口，客户端会先确认文件已保存，再调用该消费者。共享内存只保留尚未消费的候选，并限制待处理数量及总容量。

当前高可达站位链路在 `make_candidates(..., background=True)` 中启用后台保存。旧调用保留默认的同步文件接口，供仍需直接读取文件的历史工具使用；ZeroGrasp 的候选生成通过同一套共享内存接口交接。
