# V8 一秒级完整规划优化调研

2026年11月27日。依据已有正式记录、当前执行源码及官方文档整理。

目前还有值得做的优化。最优先的是把候选检查中的机器人状态更新、场景更新和文件留档拆开，使一次抓取请求中的不变几何只准备一次。接着优化失败候选的求解成本，最后再评估原生C++执行。普通场景的一秒级规划可以作为下一轮目标；复杂场景的平均值和P90需要通过完整对照确定。

## 计时从哪里开始

本轮7.198秒来自`shared_gpu2_20261127_01`原方法的10次请求，覆盖五个场景、每场景重复两次，在共享GPU2上交替测试。计时开始时，感知和候选后处理已经完成，候选通过共享内存交给规划器；计时结束时，规划结果及本轮要求的记录已经返回。

这里的“机器人模型”是运动学、关节限制和871个碰撞球的表示。“场景绑定”是把已取得的桌子、物体和停放臂几何放进当前规划坐标系。SAM3分割、RaySt3R重建和GraspGenX生成候选在这段计时之前。

若将目标定义为“GraspGenX原始输出到准备执行不超过一秒”，后处理也要纳入同一计时。下一轮应同时记录这段总耗时和规划器内部耗时。

## 当前真正花时间的地方

下表为原方法一次完整请求的平均值。各项扣除了已包含的子调用。

| 环节 | 平均耗时 | 每请求平均调用次数 | 当前观察 |
| --- | ---: | ---: | --- |
| 机器人与场景绑定 | 3.183秒 | 15.0 | 夹爪开度、目标是否纳入碰撞和手臂切换都会进入更新流程 |
| 接触几何更新 | 0.643秒 | 9.8 | 使用独立的无桌面碰撞器及V2真实夹指网格检查 |
| 抓取IK | 1.403秒 | 9.8 | 原生完整场景IK，失败后还有原几何IK与接触复核 |
| 路径搜索与两段轨迹优化 | 0.445秒 | 路径搜索2.4次 | 多数时间尚未花在最终路径优化上 |
| 其余步骤 | 1.524秒 | — | 开合爪、终点几何、其他IK、状态映射、交接与记录等 |
| 合计 | 7.198秒 | — | 中位6.079秒，P90为12.328秒 |

即使把3.183秒绑定全部消除，剩余仍为4.016秒；连接触几何更新也全部消除，仍为3.373秒。因此一秒目标需要同时降低绑定、候选求解及其余调度成本。

## 代码审查得到的具体问题

规划器和机器人模型已经常驻。`FastPlannerPool`也已实现夹爪移动副的仿射更新，记录中的运行期机器人配置构建次数为0。

剩余重复工作主要出现在以下位置：

| 位置 | 当前处理 | 可以进一步拆开的部分 |
| --- | --- | --- |
| `modules/maniskill/resident_planner.py:bind_inputs` | 读取参考配置，生成当前开度的YAML、场景JSON及名义闭爪配置，复核网格内容 | 常驻不变的配置与几何；当前关节、开度和障碍位姿使用内存数据传递；按请求快照统一留档 |
| `modules/maniskill/resident_planner.py:PlannerPool.bind` | 遍历多份运动学参数，逐项比较静态张量、复制参数，清空并重装多套场景，再执行实测FK和起始碰撞检查 | 固定属性在模型版本准入时验证；仅更新变化的数值；不同碰撞视图保留自己的状态 |
| `modules/curobo/fingertip_contact/planning.py:contact_view` | 缓存标识包含输出目录；更新时复制参数、清空并装载无桌面场景 | 将几何与状态版本作为缓存依据，输出目录仅负责记录；保持当前桌面和夹爪状态及时更新 |
| `modules/curobo/fingertip_contact/validator.py` | 多次将GPU判断与关节数据传回CPU，再进行细几何检查 | 原生判断尽量合并回传，真实网格计算只处理需要它的状态 |

这里的场景更新不等于每次重新编译CUDA Graph，也不能直接等同于每次重建网格BVH。下一次计时需要将配置处理、静态比较、场景装载、动态张量复制、GPU等待和文件写入分别标出来。

PyTorch官方性能指南指出，GPU结果参与Python分支、转回CPU及标量读取都可能引入同步。当前绑定中的逐项GPU比较与多次CPU回传值得单独测量，再将不变属性检查移到模型版本准入，将实时检查合并执行。[PyTorch性能指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)

## 优先实施的三个方向

| 顺序 | 具体修改 | 与已经做过的尝试有什么不同 | 通过什么判断效果 |
| --- | --- | --- | --- |
| 1 | 将一次请求拆成模型准入、场景快照更新、夹爪开度更新、候选求解和记录提交。模型固定属性常驻；同一几何只更新障碍位姿；夹爪只更新原URDF推导的动态参数 | 之前缓存仍进入原绑定框架，生成文件并做完整签名和校验；这次改为内存数据接口，文件由快照生成，缓存不受输出目录影响 | 每请求只在场景或碰撞视图真正变化时装载几何；比较完整耗时、全部FK、碰撞判断和所选抓法 |
| 2 | 每臂先按原方法检查首个候选，失败后再升到4或16个候选的小批量。按原评分消费结果；不同开度通过真实夹爪状态检查 | 最新固定窗口虽取消串行凑批，仍计算154个抓取终点，其中56个未使用；这次按失败情况扩批，减少未消费工作。不能靠取整开度凑批 | 同时记录实际消费数、提前计算数、原方法回退次数；只在完整请求变快且成功保留时采用 |
| 3 | 将数值IK、碰撞判断和需要的CPU结果交接合并，减少小调用和同步；如果Python路径仍占较多成本，再接原生C++ | 解析IK的GPU批量查询已经约11毫秒，但84/98个抓取终点仍回到原IK。仅重复调用解析内核不能解决这部分成本 | 分开统计成功终点、无合格解析分支、碰撞分支及数值回退；用同一目标、原种子和精度验证完整收益 |

官方支持在固定张量布局下更新锁定关节数值、更新障碍物位姿，并保留规划器与碰撞缓存。左右臂可以保留兼容的求解上下文，共享适合共享的几何；夹爪开度需要按实际值更新。当前ARX实际行程与近桌抓取要求保持。[官方运动学更新接口](https://nvlabs.github.io/curobo/latest/api/curobo.kinematics.html)、[维护者关于多臂与锁定关节的说明](https://github.com/NVlabs/curobo/issues/668)

场景快照的键应包含资产几何版本、障碍位姿、规划基座、停放臂、目标纳入规则及接触策略。夹爪开度与实测关节状态分别维护。场景变化后同步更新相关视图，并清除旧场景的路径搜索节点。

固定配置校验可以前移到模型准入；实测FK、起始碰撞、当前障碍和完整路径检查仍随请求执行。留档可以由后台线程处理，但记录错误仍要传回调度器，执行放行仍使用原记录完整性要求。

## 已经失败的方向如何处理

| 已有尝试 | 实际结果 | 本次调研的取舍 |
| --- | --- | --- |
| 相同场景只更新开度 | 完整绑定13.0→5.2次，但累计耗时增加0.44% | 不重复启用这份包装器；首先拆出其余配置、同步与留档成本 |
| 预抓取并行4条路径，提前寻找合格终点 | 平均4.110→5.615秒，额外检查82个终点 | 不再提前串行凑齐一批 |
| 固定16个原候选批量端点＋并行路径 | 平均7.198→8.959秒；98→154次抓取终点计算 | 扩大批量没有成为下一步重点；先减少无用工作和每次更新成本 |
| 解析IK接入完整规划 | 平均4.240→4.377秒，84/98个抓取终点仍回原IK | 分析回退来源，再决定如何接入，保留原目标精度 |
| 512球替换871球 | 右指尖新增外包误差明显，原几何拟合核查未通过 | 本轮继续871球 |
| 稀疏可达性地图初值 | 既有E对照没有完整收益 | 继续作为初值辅助研究；地图空缺不作为删除候选的条件 |

这些表格来自各自的同期对照。不同批次的GPU负载和运行时间不同，各轮收益不直接相加。

## 新方法调研结果

| 方法 | 官方提供了什么 | 与我们的问题的关系 | 优先级 |
| --- | --- | --- | --- |
| cuRobo原生C++运行时 | 支持IK、路径、轨迹优化、网格场景与抓取流程；机器人和内核可以预先导出并复用 | 可以减少Python调度与转换。ARX的动态夹爪宽度、左右臂和V2真实网格接触需要逐项适配；原生导出的锁定关节数值不能直接假定支持动态更新 | 结构更新完成后验证 |
| cuRoboV2-Fast | B样条优化、GPU RRT、计算内核优化及TimeOpt；官方RTX5090、3千克负载基准平均规划4.4毫秒 | 说明核心规划计算有很低延迟的实现。它的指标不包含我们的候选后处理、多次绑定和全部ARX适配；需核对本机已有源码中的模块及实际调用路径 | 后续独立比较路径求解部分 |
| VAMP / VAMP-MR | 用CPU SIMD批量执行FK和碰撞，支持快速采样规划 | 可以研究路径和细检查，但需要适配ARX及当前场景表示。当前路径部分仅0.445秒，替换它本身不足以达到一秒 | 暂后于前两项 |

cuRobo原生运行时的官方说明要求复用实例、场景和缓冲区，预热代表性请求，并指出导出配置与Python配置需要一致。动态锁定关节仍要核对实际公开接口。[C++运行时](https://github.com/NVlabs/curobo/tree/main/cpp_runtime)、[官方集成流程](https://github.com/NVlabs/curobo/blob/main/AGENTS.md)

cuRoboV2-Fast发表于2026年11月4日，11月9日修订。其抓取集成先用IK筛选抓姿，再规划预抓取、接近和抬升；论文明确区分了终点可行与完整路径可行。这一做法支持先降低候选检查成本，再对少量合格目标求路径。[论文项目主页](https://research.nvidia.com/labs/lpr/curobov2-fast/)

VAMP提供自定义机器人代码生成路径，当前场景支持基本几何与点云；我们使用的精细网格与V2局部接触仍需接入。[VAMP官方源码](https://github.com/KavrakiLab/vamp)、[VAMP-MR项目主页](https://vamp-mr.github.io/vamp-mr/)

## 如何验证是否真正接近一秒

先给完整规划设下列工程预算，用下一轮实测检查每一项。

| 部分 | 控制目标 |
| --- | ---: |
| 场景、机器人状态与接触上下文更新 | 0.20秒 |
| 候选终点求解、原碰撞与精细几何检查 | 0.30秒 |
| 完整路径搜索与轨迹优化 | 0.30秒 |
| 开合爪检查、调度、必要交接及记录提交 | 0.20秒 |
| 合计目标 | 1.00秒 |

建议先在原五个场景上分别比较“当前方法／内存状态更新／再加按失败扩批”，取得逐项成本。随后使用冻结的69份有效候选确认不同目标下的均值、中位数和P90，单列规划不出来的场景。若从原始GraspGenX输出开始计时，再把后处理加入同一组完整对照。

机器人、场景初始条件、871球、TCP43、V2指尖余量、候选姿态与排序、关节限制和最终精度保持。保留全部候选与原方法回退，验证时不能靠提前超时或删除难例达到一秒。

本次完成现有记录的CPU分析、源码审查及外部调研，新增GPU调用和仿真为0。分析数据保存在`tmp/planning_latency_research/one_second_20261127_01/analysis.json`。后续优化从一次请求内部的分项计时与内存状态更新开始。
