## 第1项：缓存已经处理好的停放臂几何

当前双臂适配器把停放臂合成为一份PLY网格。苹果例约6.04MiB，包含387546个原始顶点、129182个三角形。底层加载时合并重复顶点，得到64026个顶点；这一步CPU抽查约需0.16～0.20秒。同一份几何进入不同检查器时，会重复经过加载和处理。

第一项保留原几何生成与处理方法，把处理完成的结果缓存起来：

1. 首次遇到某份几何时，使用原来的加载参数完成读取、缩放和顶点处理，保存顶点数组、三角形索引及元信息。
2. 后续加载相同几何时，直接提供这些数组。独立检查器和接触检查器都可以读取同一份CPU结果。
3. 缓存标识由几何文件内容哈希、缩放参数、处理选项及处理库版本构成。文件名相同而内容变化时，生成新条目；文件路径不同而内容和处理条件相同时，可以复用。
4. 世界坐标下的停放臂网格仍按原方法生成。底盘、升降或停放臂关节变化导致几何内容变化时，重新处理并登记新条目。
5. 缓存通过统一接口提供只读数据。内存条目有容量限制；磁盘缓存使用数组文件和JSON元信息，便于核对和清理。

这一项的主要验收指标是：在同一批输入下，同一几何和处理条件只进行一次CPU处理；后续消费者的顶点和面索引与原方法逐值一致。分别记录首次处理耗时、内存命中耗时、磁盘命中耗时以及完整场景更新耗时。

## 第2项：共享GPU几何资源

在第1项的CPU结果之上，再复用GPU资源。目前不同检查器各自拥有Warp网格缓存，同一几何可能被分别上传、分别创建BVH。BVH用于加速查询机器人是否碰到三角网格。

具体采用“共享几何，各自维护场景状态”的方式：

| 数据 | 存放与更新方式 |
| --- | --- |
| 顶点、三角形和对应Warp网格/BVH | 同一进程、同一CUDA设备内，按几何内容复用 |
| 网格本地包围范围 | 与对应几何版本一起缓存，供各检查器复制使用 |
| 障碍物位置、启用状态、槽位、名称映射 | 各检查器独立维护 |
| 当前关节、夹爪开度、碰撞球和规划状态 | 沿用各自原有更新流程 |

先接入规划器和独立检查器，再让精细接触检查器通过相同接口取得需要的网格。各检查器使用的障碍集合、桌面处理和目标接触规则仍由其自身决定。

资源池保存网格的强引用，记录各检查器正在使用的资源。清理时先完成必要同步，再释放已经没有消费者使用的网格，避免沿用原来的单检查器清理方式而提前释放共享资源。

接入网格句柄时，同时更新原有尺寸、包围范围、名称和计数。当前原生`update_from_warp_id`接口会将包围范围设为无穷，因此需要补齐与原加载结果相同的几何元数据，保持现有碰撞计算和加速行为。

验收时，比较各检查器的完整碰撞结果、距离及梯度；专门检查“一套场景关闭目标、另一套仍检查目标”“一套场景移动障碍、另一套位置保持”“释放一个消费者、其他消费者继续查询”。记录实际CPU处理次数、GPU上传次数、BVH创建次数、命中次数和峰值显存。

## 第3项：用固定槽位处理切臂和容量问题

钥匙链、马克杯、茶壶三个杂乱场景各有目标、6个干扰物和停放臂，共8个网格。当前做法把左右臂对应的几何都加入复用合集，合集达到9个便重新装载。三例实际分别出现6、4、5次重装类调用。

改为按当前场景的物理角色分配槽位：

| 障碍类型 | 更新方式 |
| --- | --- |
| 桌子和地面 | 继续使用原有长方体存储，位置或尺寸变化时更新对应数据 |
| 目标和干扰物 | 每个物体使用固定网格槽位，按内容和位姿更新 |
| 停放臂 | 使用一个固定槽位；切换活动臂时，替换该槽位的几何句柄及位姿 |
| 阶段暂时不参与检测的目标 | 保留槽位，通过原有碰撞策略切换启用状态 |

左右停放臂的几何可以同时存在于第2项的资源池里，但当前碰撞场景的停放臂槽位只引用其中一个。当前每个检查器仍使用原来的8个网格容量。

每次绑定比较几何、位姿和启用状态：几何相同则复用；位置变化只更新位姿；检测规则变化只更新启用标志；单个障碍几何变化则只替换其槽位。新增场景或整体配置变化时，才执行对应的初始化。

这一项同时处理每次请求开始清空复用记录的问题：为每套场景维护版本，所有改变场景的入口都更新版本；切回原方法、外部更新或异常中断时，将受影响的记录标为失效，再按当前实测输入完整同步。版本核对覆盖后，才能保留跨请求复用记录。

验收使用原三例执行右→左→右切换、目标启停、位置变化、请求结束再进入以及异常后重新同步。逐次比较障碍集合、位姿、几何、启用标志和碰撞结果；确认切臂时使用8个以内的槽位，并取消因9个几何合集产生的额外重装。

## 验证顺序与耗时统计

每一项依次完成下面的验证，再整理其结果并推进下一项。

| 顺序 | 验证内容 | 通过条件 |
| --- | --- | --- |
| 1 | CPU几何及更新逻辑核验 | 几何结果一致；内容变化正确失效；真实三例的缓存容量问题被覆盖 |
| 2 | GPU组件核验 | 同一批关节状态下，各检查器的FK、碰撞、距离及梯度满足原核对标准；共享与释放正确 |
| 3 | 五场景完整纯规划先导 | 原候选顺序、规划成败、选中抓法及手臂保持，终点和路径通过独立复核 |
| 4 | 整理分项及完整请求计时 | 明确首次加载、请求内复用和跨请求复用各自收益，再确定该项是否并入后续基线 |

先导场景提前固定为以下五例：

| 场景 | 选取原因 |
| --- | --- |
| M0001_S1_open_apple | 普通场景，检查基本加载与复用 |
| M0010_S1_open_boxed_food | 候选检查及绑定较多，检查重复调用成本 |
| M0062_S4_clutter_keychain | 原6次重装，覆盖容量与频繁切换 |
| M0066_S4_clutter_mug | 原4次重装，覆盖目标和停放臂切换 |
| M0078_S4_clutter_teapot | 原5次重装，覆盖杂乱场景复用 |

每项先导采用每场景4次ABBA或BAAB交错对照，共20次纯规划请求；A为上一项已验收实现，B为新增这一项。三项先导合计最多60次请求。某项总耗时增加时，保留其独立结果，后续对照基线继续使用已验收版本。

三项完成后，对通过验收的最终组合，与当前内存更新基线进行一次68场景完整配对比较，共136次纯规划请求。保持完整配对场景，不根据先导结果重新挑选输入。

每次对照在同一张卡执行，沿用当前资源门槛并允许GPU2共享。预热覆盖求解器和内核；正式几何的首次加载单独记录，并计入完整请求。两组使用可核对的等价缓存起点，分别记录冷加载和复用状态，避免一组提前加载另一组才要使用的几何。

新增计时至少包括：CPU文件读取、顶点处理、CPU缓存查询、GPU数组上传、BVH创建、几何句柄绑定、位姿更新、启用状态更新、场景更新总计，以及完整初始规划请求。报告平均数、中位数、P90、调用次数和峰值显存，检查分项相加与完整计时的对应关系。

每项分别报告实施结果、记录完整性、实际发生的更新事件及关键事件覆盖。实际抓取验证另行登记，使用最终通过的组合。
